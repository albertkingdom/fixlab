# 第 9 篇：限制測試程式能做什麼（沙箱）

> 對應任務：bootstrap-agent-core 的 5.1。
> 完成度：基本規則完成，在 macOS 上有效（寫這篇時全部測試 172 個通過，其中 11 個是這一篇的）。「測試檔不可被寫入」的系統層規則是下一個任務 5.2，這一篇還沒有。

前面的工具大多只是讀檔、改檔。`run_tests` 不一樣：它會**真的執行**專案裡的程式，而專案裡有一部分是模型剛改寫過的。換句話說，模型寫的程式碼，在你的電腦上，用你的帳號權限跑起來了。

這一篇要回答：跑的時候，該不該限制它？限制什麼？

先老實說一件事：**到目前為止，沒有任何一次真模型的修復做過危險的事。** 六次真實紀錄裡，模型寫的都是正經的修正。這一篇的理由不是「已經發生過」，而是「發生一次就來不及了」：風險是推論出來的，不是量到的。

## 三種風險

被執行的程式可以做這些事：

| 風險 | 為什麼可怕 |
|---|---|
| **連網路** | 可以把讀到的東西送出去 |
| **讀你的機密檔** | 家目錄裡有 `~/.ssh`（連線用的私鑰）、其他專案的 `.env`（放金鑰的檔案）。就算不能連網，讀到的內容也可能印在測試輸出裡，而測試輸出會原封不動送給模型供應商 |
| **寫到別的地方** | 改掉你家目錄裡的檔案、改掉別的專案 |

最後一種不一定是惡意。模型寫錯一個路徑，就可能把檔案寫到不該寫的地方。

## 先講三個詞

- **沙箱（sandbox）**：把一個程式關進一個有限制的環境執行，它只能做被允許的事。
- **`sandbox-exec`**：macOS 內建的指令，用法是 `sandbox-exec -p 規則 指令…`，規則裡寫什麼能做、什麼不能做。
- **規則的語言**：這個指令的規則是用一種括號很多的小語言寫的，叫 SBPL（Sandbox Profile Language）。長得像 `(deny network*)`，意思是「禁止所有網路動作」。

## 先寫一個最天真的版本

沒有沙箱時，`run_tests` 就是直接執行：

```python
def run_v1(root):
    return subprocess.run([sys.executable, "-m", "pytest", "-q"], cwd=root)
```

（`run_v1` 只存在這篇文章裡，專案裡沒有它。）

要看它能做什麼，需要一組「探針」：寫一個測試檔，裡面試著做一件事，把結果（做得到 `ok`，被拒絕 `denied`）放進失敗訊息裡讓我們讀。探針跑的是真正的 `run_tests`，只有沙箱的開關不同。為了安全，用的是假的金鑰檔（`sk-fake-123`）和本機的 TCP 伺服器，不會真的連到外面。

真實輸出（沒有沙箱那一欄）：

```
動作                              沒有沙箱        沙箱
連到本機的 TCP 伺服器                 ok          denied
讀家目錄裡的假金鑰檔                    ok          denied
列出 ~/.ssh 的檔名                 ok          denied
讀 fixlab 專案的 pyproject.toml   ok          denied
寫家目錄                          ok          denied
寫 /tmp                        ok          denied
寫工作目錄                         ok          ok
讀工作目錄                         ok          ok
```

「沒有沙箱」那一欄全部是 `ok`：什麼都做得到。右邊那一欄是下一節的結果。

## 最後的規則

```
(version 1)
(allow default)                          ← ① 預設全部允許
(deny network*)                          ← ② 禁止網路
(deny file-read* (subpath (param "HOME")))      ← ③ 禁止讀家目錄
(deny file-read* (subpath (param "PROJECT")))   ← ④ 禁止讀 fixlab 專案目錄
(allow file-read* (subpath (param "WS")) (subpath (param "VENV")))   ← ⑤ 放行自己的工作目錄與虛擬環境
(allow file-read-metadata)               ← ⑥ 放行「看得到檔案存在」
(deny file-write* (require-not (require-any   ← ⑦ 寫入：只有這三個地方
    (subpath (param "WS")) (subpath (param "TMP")) (subpath "/dev"))))
```

這份規則有幾個地方需要解釋。

**後面的規則會蓋過前面的。** 所以順序就是邏輯：③④先禁止讀整個家目錄，⑤再把工作目錄放回來。如果你的專案放在家目錄底下（很常見），順序顛倒的話，工作目錄自己也讀不到。有一個測試專門驗證「工作目錄在家目錄底下仍然能跑」。

**為什麼不是「預設全禁止，再一項一項放行」？** 這樣更嚴，但 Python 和 pytest 啟動時要讀的系統路徑很多（系統函式庫、時區資料……），列不齊，漏一個就整個起不來。所以選了「預設允許，再把危險的收掉」。取捨：它擋不到沒想到的地方，例如 `/etc` 底下的設定檔現在還是讀得到。

**⑥為什麼要放行「檔案資訊」？** 程式要知道「目前在哪個目錄」，作業系統得走過每一層上層目錄。只要上層目錄的「內容」被禁止讀，連「它存在」都看不到，程式一啟動就失敗。放行資訊（存在與否、大小），內容仍然讀不到。

**⑦的 `/dev`：** 程式常常寫 `/dev/null`（丟棄輸出）。不放行會出很怪的錯。

**路徑為什麼是 `(param "WS")` 而不是直接寫路徑？** 見下面的問題三。

套上這份規則後（上面對照表右邊那一欄）：網路被拒、家目錄和專案目錄讀不了、寫入只剩工作目錄；工作目錄本身讀寫照舊。範例專案在沙箱裡跑的結果和以前一樣：

```
1 failed, 4 passed in 0.01s     （範例專案原本就有一個 bug，所以是 1 failed）
```

## 沙箱怎麼接到 run_tests

```python
def run_tests(ws, target="."):
    command = [python, "-m", "pytest", ...固定的參數..., "--", target]
    with 建立這次專用的暫存目錄() as tmpdir:
        if 有沙箱可用():
            command = 用沙箱包起來(command, 工作目錄, tmpdir, ...)
        done = subprocess.run(command, cwd=工作目錄, env=乾淨的環境變數(tmpdir), ...)
    ...
```

只有 `run_tests` 在沙箱裡。其他工具（讀檔、改檔、搜尋）是 fixlab 自己的 Python 行程在執行，它們靠的是前面做的路徑檢查，不在沙箱裡。這跟 Claude Code 一樣：它的官方文件說，沙箱只套在執行指令的工具上，檔案工具不在沙箱裡。

## 做的時候踩到的三個問題

### 問題一：路徑一定要用「真實路徑」

macOS 的 `/var` 其實是 `/private/var` 的捷徑（符號連結）。系統暫存目錄叫 `/var/folders/…`，但作業系統比對規則時用的是真實路徑 `/private/var/folders/…`。用捷徑寫的規則永遠對不上。

用同一個工作目錄，規則裡的路徑只差「原樣」和「真實」（真實輸出）：

```
暫存目錄的寫法 : /var/folders/sd/…/tmp1t9xglmd/ws
真實路徑       : /private/var/folders/sd/…/tmp1t9xglmd/ws
規則裡的 WS 用原樣的路徑  ：PermissionError: [Errno 1] Operation not permitted: 'ok.txt'
規則裡的 WS 用真實路徑    ：written
```

最討厭的是：錯誤訊息只有「不允許」，連工作目錄本身都寫不進去，完全看不出原因是路徑寫法。所以現在傳給規則的路徑一律先轉成真實路徑，並有一個測試用「符號連結形式的工作目錄」確保這點。

### 問題二：pytest 的暫存檔偷偷寫進工作目錄

pytest 有個功能叫 `tmp_path`：測試需要暫存檔時，它在系統暫存目錄建一個資料夾給測試用。沙箱不准寫 `/tmp` 之類的地方，你可能以為這種測試會失敗。實際上它通過了，這更糟：

```
沒有沙箱                        : 1 passed in 0.00s ｜工作目錄多出： 無
沙箱、TMPDIR 沿用系統的         : 1 passed in 0.00s ｜工作目錄多出： ['pytest-of-yklin', 'pytest-of-yklin/pytest-0', '...']
```

測試**通過了**，但工作目錄裡多了一個 `pytest-of-使用者` 資料夾。原因我另外確認過：Python 找暫存目錄時，會依序試幾個候選位置，都寫不進去就退回**目前目錄**：

```
沙箱、系統的 TMPDIR : /private/var/folders/…/tmpadgby08a/ws     （就是工作目錄本身）
沒有沙箱            : /var/folders/sd/nwmvs5897lg88p6gp3zh8w9h0000gn/T
```

這會弄髒結束時的差異比較（`fixlab` 結束後會把「改了什麼」印出來，多出的暫存資料夾會混進去），而且是悄悄發生的。

解法是**每次執行建立專用的暫存目錄**：把它放進沙箱的寫入白名單、讓子行程的 `TMPDIR` 指向它、跑完整個刪掉：

```
最終的 run_tests（私有暫存目錄）: 1 passed in 0.00s ｜工作目錄多出： 無
跑完後留下的 fixlab-run-* 目錄  : 0
```

測試通過、工作目錄乾淨、也沒有留下暫存資料夾。

為什麼不直接放行整個系統暫存目錄？因為那是所有程式共用的，被測程式可以看到、也可以改別的程式留在那裡的檔案。專用的目錄只屬於這一次執行。（Claude Code 的做法是放行「每個使用者專屬的暫存目錄」，粒度比較粗，這裡刻意更細。）

### 問題三：路徑不能直接拼進規則文字

最直覺的寫法是把路徑拼進規則字串：`f'(subpath "{ws}")'`。如果資料夾名稱剛好含引號，規則文字就壞了。用一個叫 `my "quoted" (project)` 的資料夾試（真實輸出）：

```
天真版 -> 65 sandbox-exec: Error reading string
最終版 -> 0 ran and wrote
```

天真版連規則都讀不進去，指令根本沒跑。這種「壞掉」至少是安全的（沒跑就不會做壞事），但測試也就跑不了。現在的做法是路徑一律用 `-D 名稱=路徑` 這個參數傳進去，規則裡只寫 `(param "WS")`：路徑裡有什麼字元都只是「資料」，不會被當成規則。有一個測試確認規則文字裡完全沒有字面路徑。

承認一點：真的用引號命名資料夾的人很少，這個保護多半用不到。但它成本很低，而且規則是安全邊界，不該讓檔名有機會改寫它。

## 沒有沙箱的平台

`sandbox-exec` 只有 macOS 有。在其他平台，`run_tests` 直接執行、不套沙箱。但**不能悄悄不啟用**：`fixlab PATH` 一開始會在 stderr 印一行狀態：

```
sandbox: on
sandbox: OFF (not macOS: tests run without a sandbox)
sandbox: OFF (sandbox-exec not found: tests run without a sandbox)
```

（上面是三種可能的輸出；這台是 macOS，印的是第一行。）

Claude Code 對 Windows 的處理也一樣：官方文件寫，沙箱在 macOS 和 Linux／WSL2 上可用，原生 Windows 上指令不經沙箱直接執行；而且它在沙箱起不來時預設也是直接執行，另外提供一個 `failIfUnavailable` 設定，改成「起不來就中止」。我們採同樣的預設（照跑，但讓使用者看到），「起不來就中止」的選項先不做，列在已知限制。

另外有一個容易漏掉的情況：如果沙箱啟動後 Python 本身起不來（例如指定的直譯器路徑不存在），這**不算測試通過**，會是失敗。有一個測試專門確認這點。

## 怎麼驗證

測試在 `tests/test_isolation.py`（10 個）和 `tests/test_cli.py`（1 個）。macOS 專用的測試在其他平台自動略過。

- **網路**：用本機的 TCP 伺服器，沙箱裡連不上；不靠外部網路，所以不會因為網路狀況而時對時錯。
- **讀取的七列表格**：額外禁止的目錄、專案根目錄的 `AGENTS.md`、家目錄的假金鑰檔、`~/.ssh`、專案的 `.git/HEAD` 都是 `denied`；工作目錄裡的檔案和虛擬環境裡的套件是 `ok`。
- **寫入**：家目錄被拒；工作目錄外被拒、工作目錄內可以。
- **規則文字**裡沒有字面路徑。
- **符號連結形式的工作目錄**、**工作目錄在家目錄底下**都能正常跑。
- **`tmp_path` 不弄髒工作目錄**。
- **指定的直譯器起不來不算通過**。
- **沒有沙箱時照跑，且狀態行這樣說**。
- **CLI 一開始會印出狀態行。**

這些測試有沒有用，還要確認「它們真的能分辨有沙箱和沒沙箱」：用同樣的探針，把沙箱關掉，原本該是 `denied` 的全部變成 `ok`（就是上面那張對照表）。如果測試在沒有沙箱時也通過，那它什麼都沒測到。

## 已知限制

- **只有 macOS 有效。** 而且 Apple 已經把 `sandbox-exec` 標為棄用，雖然目前還能用，之後可能消失。沙箱的介面集中在 `sandbox.py` 一個檔案，將來要換成容器（Docker）只改這裡。
- **擋不到沒想到的地方。** 因為是「預設允許」，家目錄以外的機密（例如 `/etc` 底下的設定）仍然讀得到。
- **基底 Python 裝在家目錄底下會起不來。** 例如用 pyenv 或 uv 管理的 Python：家目錄整個被擋了。目前這台的 Python 在 `/opt/homebrew`，不受影響；遇到時需要把它的位置加進放行清單。
- **寫到固定位置的程式會被擋。** 例如測試把檔案寫到 `/tmp/某個名字`，在沙箱裡失敗。失敗會顯示在測試輸出，不會被當成通過。範例專案沒有這種測試。
- **硬連結。** 工作目錄裡可以放一個硬連結指向外面的檔案，而沙箱只檢查路徑，不認得它。階段 1 不處理。
- **測試檔還沒受到保護。** 沙箱現在擋的是工作目錄**以外**的東西；被測程式仍然可以改寫工作目錄裡的測試檔。第 4 篇提過模型改測試檔的情形；改檔與寫檔工具已經擋住了直接改，但 `run_tests` 執行的程式自己寫檔，工具層管不到。「測試檔在系統層不可寫」是下一個任務 5.2。
- **逾時只殺最上層的行程。** 測試若再啟動子行程，逾時後孫行程可能留在背景。目前的範例專案碰不到。
- **沒有真實案例。** 這些保護都是預防，不是修了一個已經看到的問題。

## 參考來源

- **高見龍 KeSi**（`kesi.py` 的 `sandbox_spec`，MIT 授權，Copyright (c) 2026 Eddie Kao，commit `dfa0cd0`，2026-10-17 查證）：**採用的想法：** 「預設允許，再逐項收緊」（他的註解寫明：預設拒絕更嚴，但系統需要的路徑列不全，shell 會直接中止）、路徑用 `-D` 參數傳而不是拼進規則、放行檔案資訊讓程式能取得目前目錄、寫入只放行白名單。他的專案也有一個 `sandbox_status()`，沙箱不可用時退回直接執行並顯示狀態；本專案的函式名稱與做法相同，不能排除受他影響。**不同的地方：** 他擋 `/Users` 與 `/Volumes` 並放行家目錄下的工具鏈資料夾，這裡擋家目錄與 fixlab 專案目錄；他放行系統共用的暫存目錄，這裡每次執行建一個專用的；他的規則還用正規表示式擋掉工作目錄裡的特定名稱（例如 `.env`），這裡不做。因為結構相同，`sandbox.py` 的檔頭附上了他的授權全文。
- **Claude Code**（官方文件〈Sandboxing〉，2026-10-17 查閱）：沙箱在 macOS（Seatbelt）與 Linux／WSL2（bubblewrap 加 socat）上可用；原生 Windows 上指令不經沙箱；沙箱不可用時預設直接執行，可用 `sandbox.failIfUnavailable` 改成中止；沙箱只套在執行指令的工具，檔案工具不在其中；允許寫入的位置是工作目錄、每個使用者的暫存目錄與額外加的目錄。**採用的想法：** 「不可用時照跑，但讓使用者看得到」，以及檔案工具與沙箱分開處理。
