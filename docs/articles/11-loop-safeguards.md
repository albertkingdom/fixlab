# 第 11 篇：模型卡住時要停下來（連續失敗保險，與迴圈的測試補齊）

> 對應任務：bootstrap-agent-core 的 6.1 到 6.4。
> 完成度：完成（寫這篇時全部測試 256 個通過，比上一篇多 23 個）。這一篇分兩半：前半是一個新的保險，後半是替迴圈已有的行為補上測試，並建立一份「黃金 trace」。

第 3 篇的迴圈只有一道保險：**最多 20 步**。這一篇加第二道：模型連續好幾輪都在失敗，就停下來。

## 要防的是什麼

先老實說證據有多薄：**真實的紀錄裡，沒有任何一次是這道保險能救的。**

最接近的是任務 3.7 的唯讀探索（記錄在設計文件的風險清單；模型 qwen3.5-9b，當時只有讀檔和列檔案兩個工具，20 步用完）。它浪費的步數有兩種：

- 2 次呼叫不存在的工具（`pytest`、`open`）：這是失敗，但中間夾著成功的呼叫，**不是連續的**。
- 11 次重讀同一個 `parser.py`：這是**成功**的呼叫，只是沒有進展。

所以新的保險抓不到這兩種。那為什麼還要做？因為它的成本很低（一個計數器），而它防的情況很容易想像：模型把參數寫錯，收到錯誤，又寫錯一樣的參數，一直重複。沒有這道保險，這種模型會白白燒完 20 步的 token 才停。**這是預防，不是從資料裡看到的需求**，設計文件也這樣記。

## 先看沒有保險會怎樣

用一個**寫好劇本的假模型**（不是真模型）：它每一步都讀一個不存在的檔案。工具是真的，專案是 timelog 的副本。先把保險拿掉，只剩步數上限：

```
== 1. 模型一直用錯的路徑讀檔 ==
只有步數上限      stop=max_steps steps=20  model_calls=20  counters={}
加上連續失敗保險  stop=stuck     steps=3   model_calls=3   counters={'stuck_failures': 3}
```

20 次模型呼叫對 3 次。劇本是我寫的，所以這個數字只證明保險有作用，**不證明真模型會這樣**。

## 規則：整輪都失敗才算一次

天真的做法是「工具回 `ok=False` 就加一」。但一輪（模型的一個回覆）可以有好幾個工具呼叫，只要其中一個成功，模型就還在前進。所以規則是：

```python
# 5. 連續失敗保險：整輪的工具呼叫全部失敗才累計，只要有一個成功就歸零。
#    沒有執行工具的輪（回覆壞掉）走不到這裡，所以既不累計也不歸零。
failing_rounds = failing_rounds + 1 if round_failed else 0
if failing_rounds >= MAX_FAILING_ROUNDS:
    c["stuck_failures"] = failing_rounds
    res.stop_reason = "stuck"
    break
```

`round_failed` 由 `_run_tool_calls` 回傳：這一輪**每個**呼叫都 `ok=False`。累計到 3 就以新的 stop reason `stuck` 結束，並在計數器記下 `stuck_failures`，之後統計才分得出「卡住」和「步數用完」。

邊界情況各有一條規則，都是為了讓計數反映「模型有沒有在前進」：

| 情況 | 算什麼 | 理由 |
|---|---|---|
| 一輪裡一個失敗、一個成功 | 成功，歸零 | 有進展 |
| 工具被擋下（`blocked`，例如改測試檔） | 失敗 | 模型在做不被允許的事，重複三次就是卡住 |
| `run_tests` 的測試沒過 | **不是**失敗 | 失敗的測試是有用的資訊，工具本身成功了（`ok=True`） |
| 無效回覆、空回覆、被截斷（沒執行任何工具） | 不動計數 | 這些輪已經有自己的回饋機制（第 3 篇） |

用劇本模型把六種情況各跑一次，輸出如下：

```
== 2. 計數規則 ==
三輪全失敗                          stop=stuck  steps=3  counters={'stuck_failures': 3}
失敗、成功、失敗、失敗、完成        stop=done   steps=5  counters={}
一輪裡一個失敗一個成功 → 歸零       stop=done   steps=5  counters={}
失敗、無效回覆、失敗、失敗          stop=stuck  steps=4  counters={'parse_errors': 1, 'stuck_failures': 3}
改測試檔被擋 ×3                     stop=stuck  steps=3  counters={'blocked_calls': 3, 'stuck_failures': 3}
run_tests 測試失敗 ×3 後完成        stop=done   steps=4  counters={}
```

第四列是「無效回覆既不累計也不歸零」：失敗、（無效回覆）、失敗、失敗，總共三次失敗，第四步就停；如果無效回覆會歸零，這個劇本就不會在這裡停；如果它算一次失敗，第三步就會停。最後一列的 `counters={}` 是因為這個專案的測試本來就失敗，`tests_passed` 是假的，旗標為假不計數。

對應的測試是 `tests/test_loop.py` 的六個情境，加一個「同一輪兩個失敗只算一次」。

## 和 KeSi 的對照

高見龍的 KeSi（`kesi.py` 的 `run_agent`，commit `dfa0cd0`，2026-10-17 讀）有同樣的東西：計數器 `failures`，一輪的工具結果**全部**是錯誤才加一，有任何一個成功就歸零，到 `MAX_TOOL_FAILURES = 3` 就把一段說明寫進對話並結束。

- **採用的想法：**「整輪全失敗才算」。這在我動手前就記在 AGENTS.md 了（讀他的連載時記下的）。
- **數字 3 也一樣。**這個數字在我的設計裡沒有實測依據，不能排除是受他影響，階段 3 會用 telemetry 校準。
- **差異一：**他的 shell 工具在結束碼不是 0 時就算錯誤，所以連跑三輪失敗的測試會被判卡住。這裡 `run_tests` 失敗的測試是 `ok=True`，不計入。這是自己的需求：修 bug 的過程中測試本來就會失敗好幾次。
- **差異二：**他沒有「無法解讀的回覆既不累計也不歸零」這條，因為那是這裡的回覆回饋機制才需要的。
- **差異三：**他停下來只回傳一句話；這裡記下 stop reason `stuck` 和 `stuck_failures`，讓實驗能統計。

## 替迴圈已有的行為補測試（6.2、6.3）

回覆異常處理、重試和 trace 的程式在第 3 篇寫迴圈時就已經在了，但那時只有空回覆有測試。規格寫了這些行為，所以補上對應的測試：

| 規格的情境 | 測什麼 |
|---|---|
| 缺必要參數 | 檔案沒被改，下一個請求裡有 `invalid`，`parse_errors` 是 1 |
| 被截斷的回覆 | `finish_reason` 是 `length`：這個回覆裡的工具呼叫**不執行**，下一個請求告訴模型 `cut off` |
| 同一回覆兩個讀取 | 依序執行；兩個結果各用自己呼叫的 id 接在後面；合起來算一步 |
| 429、500、連線錯誤 | 重試一次後成功，`rate_limit_retries` 是 1（三種錯誤用參數化的同一個測試） |
| 逾時 | **不重試**，以 `error` 結束，`request_errors` 是 1 |
| 重試用完仍失敗 | 以 `error` 結束，不丟例外 |
| trace 紀錄 | 每個回覆一筆；事件是 `tool_calls`、`invalid_tool_call`、`done`；同一回覆的每個呼叫都有紀錄，包括旗標 |
| 長參數與輸出 | 超過 2000 字元在**紀錄裡**截斷，工具實際收到的仍是完整內容 |

重試的測試要自己造 openai 的例外，這需要 HTTP 的 `Request` 和 `Response`。安裝的 openai 3.31.0 改用 `httpx2`（舊版用 `httpx`），所以測試先試 `httpx2`，沒有再退回 `httpx`。

**這批測試找到一個真的 bug。**規格寫「超過 2000 字元要截斷」，程式寫的是 `< 2000`，於是剛好 2000 字元的參數也被截斷並加上 `...`。測試一寫「剛好 2000 字元要完整保留」就失敗了：

```
>       assert records[0]["tool_calls"][0]["args"]["new_string"] == exactly
E       AssertionError: assert 'xxxxxxxxxxxx...xxxxxxxxxx...' == 'xxxxxxxxxxxx...xxxxxxxxxxxxx'
E         - xxxxxxxxxxx
E         + xxxxxxxxxxx...
```

改成 `<= 2000`。影響很小（紀錄裡多三個點），但它說明了為什麼「規格寫了、程式也寫了、沒有測試」不算完成：沒有測試就沒有人看過邊界。

## 黃金 trace

前面的測試各管一個行為。**黃金 trace** 管的是整體：把「假模型修好 timelog」整個過程的對外行為存成一個檔案，之後任何改動讓行為變了，哪怕是你沒注意到的，這個測試都會失敗。

劇本是八步，用真的工具在 timelog 副本上跑：

```
1. list_files                          看專案結構
2. grep parse_duration                 找函式在哪裡
3. read_file report.py + parser.py     同一個回覆讀兩個檔
4. run_tests                           測試失敗（不算工具失敗）
5. edit_file tests/test_report.py      想改測試檔，被擋下（blocked）
6. edit_file parser.py                 真正的修法
7. run_tests                           通過
8. "Fixed parse_duration."             宣告完成
```

存下來的有兩樣：

- **假模型每次收到的完整對話**（8 次請求，訊息數依序是 2、4、6、9、11、13、15、17）加上工具名稱清單。提示文字、工具輸出格式、錯誤訊息被改，都會在這裡被抓到。
- **每一步的 trace 紀錄**（去掉耗時）、最終計數器、stop reason、token，以及修好後的 `parser.py`。

每次執行都會變的東西要先去掉：隨機的呼叫 id（`call_` 加八個十六進位字元）換成 `call_ID`、pytest 的耗時（`in 0.01s`）換成 `in Xs`、暫存目錄路徑。去掉之後連跑三次結果相同。

**它真的會失敗嗎？**我手動做了一次：把 `read_file` 的行號寬度從 6 改成 5，跑黃金測試：

```
E           AssertionError: requests
E           assert [{'messages':...tests']}, ...] == [{'messages':...tests']}, ...]
E             At index 3 diff: {'messages': [{'content': 'You are a coding agent. ...
```

失敗了，而且訊息說的是 `requests`、索引 3（從 0 算，也就是第 4 次請求，第一次帶著讀檔結果的那個）。一開始我把整份資料用一個 `==` 比，失敗時只看到「兩個很大的字典不一樣」；改成一部分一部分比（對話、trace、計數器、最後的檔案），訊息才指得出是哪一部分。改完還原，測試恢復通過。

有意改變行為的時候，用 `UPDATE_GOLDEN=1 pytest tests/test_trace_golden.py` 重新產生，然後看 `git diff`，確認每一處變動都是你要的。**重新產生不是修好測試的捷徑**，是「我確認這個變動是對的」的動作。

另外有一個輔助測試，確認劇本真的走到每一種情況（事件順序、被擋下的旗標、同一回覆兩個呼叫），避免黃金檔案只記了一半。

## 已知限制

- **`3`（連續失敗）和 `20`（步數）都是初始值，沒有實測依據。**階段 3 用 telemetry 的步數分佈校準。
- **沒有重複呼叫偵測。**唯讀探索那次的 11 次重讀同一個檔案，這道保險抓不到。要不要做、怎麼做（同樣的工具加同樣的參數連續出現幾次？），留給階段 2 看 telemetry 再決定。那次的觀察又被「沒有 `edit_file` 可用」混淆，有完整工具時是否還會發生，還不知道。
- **劇本模型不是真模型。**這一篇的所有輸出都來自寫好的劇本，證明的是程式照規則運作，不是真模型會怎麼做。
- **黃金檔案會隨有意的改動而過期。**改了提示文字或任何工具的輸出格式，它就會失敗，要重新產生。這是它的用途，也是它的成本。工具的 `description` 不在比對裡，只比工具名稱。
- **黃金劇本在 macOS 上用了沙箱。**其他平台沒有沙箱，`run_tests` 的輸出理論上相同，但我沒有在別的平台上驗證過。
