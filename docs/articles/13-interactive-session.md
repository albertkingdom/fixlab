# 第 13 篇：連續下指令（互動模式）

> 對應任務：stage2-cli-telemetry 的 3.1、3.2、3.4、3.5。
> 完成度：完成（寫這篇時全部測試 379 個通過，階段 1 結束時是 260 個；這一篇相關的是互動模式 40 個、畫面格式 34 個）。互動模式裡「寫檔前先問」那一塊留到第 14 篇，它的一部分測試也在互動模式那 40 個裡。

到目前為止 `fixlab PATH` 是一次性的：你給一個目錄，它修完，印結果，結束。這一篇讓它能在同一個目錄上連續聽你下指令。

## 一次性模式不夠用的地方

修完 bug 之後，你很可能接著想說「幫那個函式加上說明文字」。這句話裡的「那個函式」要靠上一輪的內容才懂。一次性模式每次都從零開始，沒有上一輪。

## 最天真的版本：每一行各跑各的

最直覺的互動模式只是在外面包一個迴圈：

```python
while True:
    line = input("fixlab> ")
    run_agent(client, model, ws, line)    # 每一行是一個全新的任務
```

這樣能動，但看看第二個任務時模型收到什麼。我用寫好劇本的假模型把兩個任務跑一遍，印出第二個請求裡每則訊息的角色：

```
2nd request roles: ['system', 'user']
```

只有系統提示和這一句話。模型看不到第一個任務讀過什麼、改了什麼、結論是什麼，「那個函式」對它沒有意義。（誠實說明：我沒有用真模型跑這個壞版本，所以不知道真模型實際會怎麼回答；這裡展示的是它收到的內容。）

## 保留對話

模型的 API 沒有狀態，不會替我們記得上一輪；它看起來「記得」，是因為每次請求程式都把整段對話重送一次。所以保留對話，就是讓第二個任務的請求帶著前面所有的訊息。

`run_agent` 本來自己在函式裡建立 `messages`，跑完就丟。現在多一個選用的參數：

```python
run_agent(client, model, ws, task, messages=None)
```

- 不傳（`None`）：和以前完全一樣，這次執行自己用，跑完就丟。一次性模式與所有舊的測試都不受影響。
- 傳一個空 list：先放入系統提示，再接任務。
- 傳一個有內容的 list：任務直接接在後面。

傳進來的 list 會被**直接修改**，所以呼叫端拿著它，就有完整的對話。這比「回傳一份新的」短，也不影響只要結果的一次性入口。

還有一個細節：模型宣告完成（回覆沒有工具呼叫）時，它最後那則回覆**以前沒有加進對話**，因為一次性模式用不到。現在要加：否則下一個任務會接在一個工具結果後面，模型自己的結論不在歷史裡。同樣的兩個任務，保留之後第二個請求變成：

```
2nd request roles: ['system', 'user', 'assistant', 'user']
```

系統提示、第一個任務、模型的結論、第二個任務。

## 真實的一次

下面是一次用真模型（qwen3.5-9b，OpenRouter）跑的互動，從事件檔讀出來（先讓模型修 timelog，再下一句「add a docstring to that function」）：

| | 任務 1：fix the failing test | 任務 2：add a docstring to that function |
|---|---|---|
| 步數 | 8 | 3 |
| token | prompt 11,766、completion 677 | prompt 6,417、completion 364 |
| 每步平均 prompt | 約 1,471 | 約 2,139 |
| 模型本身的等待（每步 `latency_s` 加總） | 13.5 秒 | 6.1 秒 |
| 任務花的時間（`task_end.seconds`） | 123.87 秒 | 16.7 秒 |

幾件事：

- **「that function」被理解了**：任務 2 只用 3 步就改好，沒有再問是哪個函式。這只是一次樣本，說明保留對話有效，不是保證。
- **對話越長，每一步越貴**：任務 2 每一步的 prompt 平均比任務 1 多約 45%，因為每一步都要帶前面任務的對話。這就是為什麼有 `/reset`（下面），也是階段 3 要看事件檔裡 `prompt_tokens` 成長曲線的原因。
- **任務花的時間包含使用者在想的時間**：任務 1 的 123.87 秒裡，模型只等了 13.5 秒，其餘是使用者讀問題、回答權限詢問的時間。所以互動模式的 `seconds` 是牆上時間，要看模型本身的延遲請用每步的 `latency_s`。

## 指令與離開

只有兩個斜線指令，外加幾種離開的方式：

| 輸入 | 做什麼 |
|---|---|
| `/reset` | 清空對話，印 `conversation cleared`；任務序號繼續往上數 |
| `/exit`、Ctrl-D、在提示字元按 Ctrl-C | 離開，退出碼 0 |
| 空行 | 忽略，不送請求 |
| 其他（包括沒定義的 `/foo`） | 當成任務 |

為什麼要 `/reset`：單一 session 的對話長度不設上限，使用者需要一個手動重來的出口，不然小模型的 context 會被撐滿。為什麼只有兩個：其他指令（看費用、看授權）現在沒有真實的需要。沒定義的 `/foo` 當成任務，是因為「/」開頭的路徑與說明文字可能就是使用者想問的內容。

## Ctrl-C：這一篇最難的部分

使用者隨時可能按 Ctrl-C。難的是它可能停在**工具呼叫和它的結果之間**。

模型的 API 要求：對話裡每一個 assistant 的工具呼叫，都要有一則對應的結果。如果對話停在「模型要求執行 `edit_file`，結果還沒回來」，這份對話之後每個請求都不合法。（這是依 API 規格；我沒有實際送出一份壞對話去測，不過高見龍的程式也為同一個問題寫了補結果的函式。）

### 第一版：整個任務丟掉

我最先的做法是最簡單的：Ctrl-C 之後，把這個任務加進對話的訊息全部截掉，回到任務開始前。對話永遠是合法的，不用想細節。

它的缺點在實作完之後才看清楚：**已經執行的修改還留在檔案裡，但對話不記得。** 例如模型已經改好了 `parser.py`，你按了 Ctrl-C，下一個任務的模型不知道檔案被改過。

### 讀了高見龍的實作，我原本否決的理由不成立

我在設計文件裡否決過「補上結果」，理由是「要猜哪些呼叫已執行、哪些沒有」。讀了他的 `run_tools` 與 `seal_dangling_tool_use` 之後發現這個理由站不住：迴圈本來就**依序**執行呼叫，中斷時知道停在第幾個。只有被打斷的那一個本身不確定（可能跑到一半）。

所以改成：**保留已完成的部分，把沒有結果的呼叫補上結果。** 補的規則：

- 已經跑完的呼叫，保留自己的結果。
- 被打斷的那一個（可能停在權限詢問、也可能在執行中），結果寫「使用者中斷了，狀態不明，重試前請先檢查現況」。
- 同一個回覆裡排在它後面、還沒開始的，寫「沒有執行」。

補結果放在迴圈裡（`fixlab/loop.py` 執行工具那一段），因為「每個呼叫都有結果」是迴圈建立的對話結構，不該由入口去猜；入口只負責接上一則「使用者中斷了這個任務」的 assistant 說明，並印出提醒。下面是實際的輸出：一個回覆要求讀檔、改檔、跑測試三個呼叫，使用者在「改檔」的權限詢問按 Ctrl-C：

```
assistant: tool_calls = ['read_file', 'edit_file', 'run_tests']
tool:      1	"""把工時字串換成分鐘數。 …
tool: error: interrupted by the user while this call was waiting or running; its state is unknown, so chec…
tool: error: not run, because the user interrupted the task
```

三個呼叫都有結果了，下一個請求合法，而且模型知道前面發生什麼。如果是在**等模型回覆時**按 Ctrl-C，對話裡還沒有任何呼叫，什麼都不用補，只接上那則說明。

### 請求失敗不一樣

請求失敗（網路、伺服器錯誤）要看任務做到哪裡：

- **還沒執行過任何工具**（第一個請求就失敗，或只收到空的、壞掉的回覆）：沒有成果可留，而且對話可能停在一則**沒有回覆**的使用者訊息，下一個任務接上去會變成兩則連續的使用者訊息，有些模型的模板會拒絕。所以整個丟掉，並印 `this task was discarded because the request failed`。
- **已經執行過工具**：改過的檔案還在磁碟上，所以和 Ctrl-C 一樣保留，接一則 `[The task stopped because the request failed.]` 給下一個任務的模型看，並提醒你檔案可能已被改過。

跑滿步數（`max_steps`）和卡住（`stuck`）也保留：對話仍然完整，使用者可以接著說「繼續」。

## 畫面

### 改版前

第一次用真模型跑的時候，畫面是這樣（路徑省略）：

```
fixlab>  fix the failing test
run_tests .
Allow? [y]es / [a]lways for this tool / [N]o: n
run_tests  ok=False  flags={'denied': True}
list_files  ok=True  flags={}
read_file  ok=True  flags={}
edit_file timelog/parser.py: replace '    units = [re.match(r"(\\d+)([hm])", text).groups()]' with '…'
Allow? [y]es / [a]lways for this tool / [N]o: y
edit_file  ok=True  flags={}
```

這個畫面很醜，而且比高見龍的還差：它是除錯用的格式（`ok=True flags={}`），沒有縮排和分層；改檔的摘要用 `repr`，所以 `\d` 變成 `\\d`；工具進度走標準錯誤、問題走標準輸出，兩個串流在終端機上交錯。

### 他怎麼做

高見龍的 KeSi 用說話者標籤（`你 >`、`KeSi >`）、縮排分層（工具呼叫兩格、授權詢問六格）、固定的方括號標籤（`[執行工具]`、`[需要授權]`、`[已擋下]`），每輪結束印一行用量與費用。沒有顏色，工具參數整個字典照印，不顯示工具結果。

### 改版後

一次工具呼叫排成一組：標題行、改檔的差異、（要問的話）問題、結果行。下面是用假模型跑出來的完整畫面（格式與真模型一樣）：

```
fixlab> fix the failing test

  ▸ run_tests .
    Allow? [y]es / [a]lways for this tool / [N]o: n
    ✗ declined
  ▸ read_file timelog/parser.py
    ✓
  ▸ edit_file timelog/parser.py
    - [re.match(r"(\d+)([hm])", text).groups()]
    + re.findall(r"(\d+)([hm])", text)
    Allow? [y]es / [a]lways for this tool / [N]o: y
    ✓
  ▸ run_tests .
    Allow? [y]es / [a]lways for this tool / [N]o: y
    ✓ 5 passed in 0.01s

Fixed parse_duration: it only took the first unit.

(5 steps · 50 + 25 tokens · 0 s)
```

規則：

- **標題行**依工具顯示它要動什麼：讀檔顯示路徑（有行範圍就加上），搜尋顯示樣式，寫檔顯示路徑與字元數，跑測試顯示目標。
- **改檔**顯示成 `-` 和 `+` 的行，每段最多 10 行、每行最多 200 字元，超過會寫 `… N more lines`。每個改檔都顯示，包括選了「一律放行」之後，因為事後也想知道改了什麼。（後來改版，任務 3.9：這樣會藏掉改動，現在改成整個檔案改前與改後的比對，只列有變的地方，前後各 3 行上下文、帶改前的行號。這裡保留的是當時的做法。）
- **結果行**：成功是 `✓`；跑測試顯示 pytest 的摘要；測試沒過是 `✗` 加摘要（工具本身成功，但對使用者來說是壞消息）；被拒絕是 `✗ declined`；被規則擋下是 `✗ blocked: 原因`；其他錯誤是 `✗ 原因`。
- 使用者打的那一行和第一組之間空一行，答案前後各空一行，最後一行是用量。
- **全部印到標準輸出**，不再有標準錯誤的進度行。
- **顏色**（綠 `✓` 和 `+`、紅 `✗` 和 `-`、用量行變暗）只在輸出是終端機、而且沒有設環境變數 `NO_COLOR` 時才開。這個慣例見 no-color.org。

### 怎麼實作

畫面的邏輯放在 `fixlab/display.py`：每個函式只回傳字串，不直接印，所以格式可以單獨測試。印出的時機由入口決定：用 `Workspace` 的一個子類別 `ShownWorkspace`，在每個工具呼叫前印標題與差異、之後印結果行。

為什麼是子類別，而不是在 `trace` 回呼裡印？因為 `trace` 是**整一步結束後**才觸發的，標題會比權限問題晚出現；一個回覆有好幾個呼叫時，順序還會亂。問題是在 `call` 裡面問的，所以標題要在 `call` 之前、結果要在 `call` 之後。另一個替代方案是在 `Workspace` 加兩個回呼參數，但只有互動入口需要，子類別就夠了。

畫面有一個整段輸出比對的測試（`tests/test_interactive.py`），把一次完整的互動（去掉耗時）逐字比對，之後誰改了格式，它會失敗。

### 為什麼不串流

高見龍的模型回覆是串流的，邊生成邊印。我們沒有做，理由是真實的數字：前面那次實跑每一步等待 1.1 到 5.0 秒、多半約 1.4 秒；8 步裡只有最後一步是文字回覆（257 個 token、2.8 秒），串流只會讓最後那則回覆早幾秒出現。

成本和風險卻比他大：他用的 Anthropic SDK 有現成的串流事件，工具參數的拼裝由 SDK 做；我們用 OpenAI 相容的 API，要自己把分段送來的工具呼叫拼回完整的呼叫，各家伺服器行為不一致，用量也要靠伺服器支援特定選項才拿得到，重試、截斷、中斷、黃金 trace 與假 client 的測試都得跟著改。等到用本機的大模型、一次回覆要等十幾秒以上的時候再做；那時先看事件檔的 `latency_s`。

## 互動模式的事件檔

互動模式寫的事件檔和一次性一樣（第 12 篇）：一個 session 一個檔，`run_start` 的 `mode` 是 `interactive`，每個任務各有 `task_start` 與 `task_end`。差別在 `task_end`：使用者在場，想驗證可以直接叫模型跑測試，所以不會自動再跑一次，`final_tests` 與 `changed_files` 都是 `null`。被 Ctrl-C 打斷的任務，`stop_reason` 是 `interrupted`，`steps`、`counters`、兩個 token 數都是 `null`（跑到一半，迴圈沒有機會回報），但 `seconds` 有量；每一步的 token 還是在 `trace` 行裡。

## 已知限制

- **沒有串流**，理由與數字見上。
- **單一 session 的對話沒有長度上限。** 用一陣子之後，每一步的 prompt 會變很大；小模型（Ollama 設 32768）可能撞到 context 上限。`/reset` 是手動出口，上限怎麼處理等有事件檔的資料再決定。
- **被打斷的那個呼叫可能已經跑了一半**（例如測試跑到一半、檔案寫了一半）。結果寫「狀態不明」，要靠模型自己去確認。
- **顏色只用假的終端機測過格式**，在真的終端機上的樣子，要實際用過才確定。
- **互動模式的耗時是牆上時間**，包含你思考與回答問題的時間。
- **不跨 session 保存對話。** 離開就沒了；這是刻意的，記憶是專案的非目標。
- **還不能在任何目錄直接打 `fixlab`。** 要用完整路徑 `.venv/bin/fixlab`，或自己把它放進 PATH；金鑰也要自己載入。這是之後要做的。
