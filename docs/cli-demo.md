# 互動 CLI Demo 操作手冊

記錄日期：2026-10-19，預計 2026-10-20 試跑。這是操作腳本與預期觀察，不是本次實跑結果。

主情境：工時報表算錯 → 模型跨檔定位 → 修改前取得允許 → 重跑測試 → 接續補上函式說明。

## 1. 準備與啟動

目前這台電腦已設定 `fixlab` 從任何目錄啟動，並自動載入 fixlab 專案的 `.env`，詳見 [本機 CLI 啟動設定](local-cli-setup.md)。若使用 Ollama，先確認服務已啟動且模型已下載；若使用遠端端點，確認可連線。

在終端機執行以下整段，每次都會建立新的範例複本。`FIXLAB_HOME` 換成 fixlab clone 所在的路徑：

```bash
FIXLAB_HOME=/path/to/fixlab
demo_dir=$(mktemp -d /private/tmp/fixlab-demo.XXXXXX)
cp -R "$FIXLAB_HOME/tests/fixtures/timelog/." "$demo_dir"
cd "$demo_dir"
pwd
fixlab
```

在目前目錄直接執行 `fixlab` 就會進入互動模式；也可用 `fixlab PATH -i` 指定其他目錄。

`fixlab` 會直接修改這份複本。不要直接拿 `tests/fixtures/timelog` 當修復目標，否則下一次展示可能已沒有原始 bug。

啟動時記下 `log: .../events.jsonl` 的路徑，之後可以查看事件紀錄。

## 2. 主 Demo：修復工時總計

在 `fixlab>` 後輸入：

```text
工時報表的總時數算錯了。請先跑測試確認問題，再找出原因並修正，最後重跑測試驗證。
```

出現 `Allow?` 時：

| 輸入 | 意義 |
|---|---|
| `y` | 允許這一次操作，主 Demo 建議用這個 |
| `a` | 這個 session 內同一工具之後都允許 |
| `n` 或直接 Enter | 拒絕這一次操作 |

預期觀察：

1. 先看到測試失敗。
2. 模型透過列檔、搜尋或讀檔尋找原因。
3. 改檔前顯示差異，詢問是否允許。
4. 修正後再跑測試，看到通過摘要。

工具順序由模型決定，提示文字不保證模型一定照做。如果模型沒驗證就結束，繼續輸入：

```text
請實際執行 run_tests，確認修改後的測試結果。
```

互動模式不會在模型結束後自動補跑測試，所以要看實際工具結果，不能只憑模型說「修好了」。

### 展示者事先知道即可

`weekly_total(["1h30m", "45m", "2h"])` 應為 4.25 小時，但原始程式回傳 3.75。測試從 `timelog/report.py` 的 `weekly_total` 發現問題，真正的 bug 在 `timelog/parser.py` 的 `parse_duration`：只讀到第一組時間單位。

展示時不要先把檔名或解法告訴模型，才能觀察它如何定位問題。也不要把固定的一行改法當成唯一成功條件；應檢查實際差異及測試結果。

可搭配說明：「這裡是模型自己決定下一步；程式提供工具、權限確認與步數上限。」

## 3. 接續任務：展示保留對話

修好後不離開，直接輸入：

```text
幫剛剛修好的函式補上 docstring，說明輸入格式、回傳單位與錯誤情況。
```

觀察模型是否理解「剛剛修好的函式」，並修改相應函式的說明。這展示同一個 session 保留前面的對話；離開後不會跨 session 保留。

專案過去已有一次真模型接續修改 docstring 的紀錄，見 [第 13 篇](articles/13-interactive-session.md)。這不代表每次都會成功。

## 4. 選做：拒絕改檔與恢復操作

建議用新的範例複本另跑一次，避免干擾主 Demo。

當模型要求 `edit_file` 或 `write_file` 時輸入 `n`，觀察工具顯示 `declined`。模型可能繼續嘗試或結束，等回到 `fixlab>` 再輸入：

```text
先解釋你打算改什麼，以及為什麼需要這樣改。這一輪不要修改檔案，等我下一個指示。
```

說明完後再輸入：

```text
可以，請修正並跑測試。
```

拒絕操作只會拒絕當次工具呼叫，不等於立刻暫停模型。若連續三輪工具全失敗，任務會以 `stuck` 結束；仍可在提示字元輸入下一個任務。已選 `a` 的工具不再詢問，這個 session 也沒有收回授權的指令，因此要展示拒絕操作時應重新開啟 CLI。

## 5. 查看事件紀錄

輸入 `/exit` 離開，使用啟動時印出的實際路徑查看紀錄：

```bash
less /替換成實際的路徑/events.jsonl
```

說明每次執行有事件檔，可追查模型設定、工具結果、token 與延遲。CLI 顯示的任務耗時包含使用者閱讀及回答權限提示的時間，不能全部當成模型等待時間。事件檔也可能包含目標專案的原始碼，公開展示前應先檢查內容。

## 6. 選做：換一個業務情境

例如購物收據與折扣碼（沿用第 1 節設定的 `FIXLAB_HOME`；新開的終端機要先重新設定）：

```bash
demo_dir=$(mktemp -d /private/tmp/fixlab-billing-demo.XXXXXX)
cp -R "$FIXLAB_HOME/bench/problems/billing/project/." "$demo_dir"
cd "$demo_dir"
fixlab
```

輸入：

```text
請讀 README 了解預期行為，執行公開測試，找出並修正問題，最後重跑測試。
```

另一題可使用 `bench/problems/inventory/project`，展示收貨單的箱、包、件換算。

只複製 `project`，不要將同題的 `solution` 或 `hidden` 放進工作目錄。這個 Demo 的公開測試通過不等於隱藏測試通過；隱藏測試成績須由 benchmark 評分器取得。

## 7. 重新開始與排查

- `/reset` 只清空對話，不會還原檔案；要重做原始 bug，先 `/exit`，再重跑第 1 節建立全新複本。
- 出現 `no model`：用 `whence -a fixlab` 檢查入口，參考 [本機啟動設定](local-cli-setup.md)。
- 測試因 Python 或沙箱問題無法啟動：保留錯誤訊息，對照 README 的已知限制；這不代表已修好 bug。
- 任務撞到步數上限或模型沒有修好：照實保留結果，檢查事件檔；不要把預期流程當成已發生的結果。

第一次試跑以第 1、2、3、5 節為主，權限拒絕與第二題可另外練習。
